## Phase 3 — Sweep bare `unwrap()` / `panic!` / `todo!` in security-sensitive paths

**Why this is useful**: 185 occurrences in 15 files. The
vast majority are in test code (where `unwrap()` is
idiomatic). The audit focuses on the **non-test**
production paths that touch security boundaries.

### Phase 3.1 — Catalogue production `unwrap()`s
1. `grep -rn "\.unwrap()" --include="*.rs" crates/ bitnet-cli/ | grep -v "/tests/" | grep -v "fn.*unwrap() in test" | grep -v "mod tests" | grep -v "cfg(test)" > /tmp/prod_unwraps.txt`
2. For each occurrence, classify:
   - **Tolerable**: parsing a `FromStr` for a known-good
     literal in a CLI dispatcher (e.g.
     `Method::from_str("ping").unwrap()`).
   - **Replace with `?` or `match`**: any path that can
     receive external input (FFI params, JSON params from
     daemon, file contents from disk).
   - **Wrap with `expect("invariant: …")`**: paths that
     logically cannot fail but the type system doesn't know.
3. Target: ≤ 5 changes. Don't sweep for the sake of it.

### Phase 3.2 — Priority files (high-signal)
In order of security sensitivity:
1. `crates/bitnet-ffi/src/lib.rs` — every FFI entry is
   called from untrusted C# code; the only `unwrap()`s
   that are tolerable are pure-from-str conversions.
2. `crates/bitnet-daemon/src/client.rs` and
   `crates/bitnet-daemon/src/daemon.rs` — IPC boundary.
3. `crates/bitnet-cli/src/main.rs` — already mostly
   cleaned (M5).
4. `crates/bitnet-core/src/lib.rs` — non-test unwraps
   (test code excluded).

### Phase 3.3 — Apply fixes
For each selected occurrence:
- Replace `.unwrap()` with `?` propagating the error, or
  `match` returning a clear `io::Error` / `CoreError` /
  `IpcError` variant.
- For `expect("invariant: …")` cases, the message must
  describe what invariant holds (e.g.
  `expect("CLIENT_OS env var is set by the launcher")`).

### Phase 3.4 — Verify
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- No new tests required (the behaviour is unchanged; we
  are just propagating errors instead of panicking).

### Phase 3.5 — Commit + push
Commit: `chore(refactor): replace bare .unwrap() in security-sensitive paths with ? or expect(invariant: …) — verified`.

**Phase 3 exit criteria**:
- Each selected `unwrap()` is replaced with `?` or
  `expect(...)` (or annotated with a `// SAFETY:` comment
  if in an `unsafe` block).
- All tests still pass; clippy still clean.
- 1 commit pushed.

## Risk register for this plan

| Risk | Mitigation |
|------|------------|
| `git stash pop` produces a conflict we cannot resolve in one round | Use `git stash apply`, manually resolve each file, then `git stash drop` only after verification. Worst case: abandon the WIP via `git checkout` of the affected files and re-author the WIP on top. |
| WIP `App.xaml` adds a resource that the test project doesn't have | The `csproj` is updated in the same WIP (adds 5 `<Compile Include>` lines). After apply, the test project should compile. |
| WIP `MainWindow.xaml.cs` overwrites our `Touch()` wiring | Read the popped file; if our H4/H5 additions are missing, re-apply them. The WIP adds a `try { AppThemeService.Load() }` block at the **start** of the constructor; our H4 wiring is in a separate code block. They should coexist. |
| `dotnet test` was not run before; the test project may have runtime issues | Run `dotnet test` (not just `build`) in Phase 1.3 and Phase 1.4 to catch any test-runtime issues. |
| Phase 3 sweeps too aggressively and breaks a path that relied on `unwrap()`-as-`expect` | Cap Phase 3 at 5 changes; if any change breaks more than 2 tests, revert and document. |
| Phase 4 finds 0 new findings (clean baseline) | That's a valid result; document the negative result and the audit trail. Don't fabricate findings. |
| The user runs out of patience mid-Phase 4 | Each phase has its own commit + push, so work is never lost. Phase 4 can be paused at any sub-step. |
