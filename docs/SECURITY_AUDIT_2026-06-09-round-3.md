**Auditor:** Hermes Agent (white-box, white-hat)
**Scope:** `crates/*`, `bitnet-cli/`, `BitNet.Desktop/` (post-WIP
helpers merge), `browser-extension/`, tests
**Code surface:** ~7 270 LOC Rust + ~3 100 LOC C# + 380 LOC TS
**Baseline:** `2a8934e` (post round 2 + WIP merge)
**Round 2 commits:** `fb90af8`, `6399934`, `770b5a8`, `2a345cd`, `a77c5ac`, `d8eacff`

This is the BugHunting **round 3** report. It audits the
**post-WIP code base** (the WIP helpers stash was merged in
Phase 1 of the follow-up roadmap before this audit started).
The audit surface is therefore larger than round 2: 8 new
helper files, 5 refactored files, 73 new test cases in
`BitNet.Desktop.Tests`.

Round 2 closed all 15 of its findings. Round 3's goal is to
find new findings in the surface that round 2 did not audit
because the WIP was not yet applied.

## 3. Findings — sorted by severity

### 3.1 HIGH (1)

#### [BITNET-H6] `SessionToken::deserialize` lacks magic / version validation
- **CWE:** CWE-345 (Insufficient Verification of Data
  Authenticity) / CWE-353 (Missing Support for Integrity
  Check)
- **File:** `crates/bitnet-core/src/session_token.rs:54-87`
- **Component:** Rust
- **Description:** The `SessionToken::deserialize` function
  parses a `Vec<u8>` blob into a `SessionToken` struct
  using only length-prefix framing:

  ```text
  ┌────────────────┬──────────────┬────────────┬────────────┬────────────┐
  │ 4B path_len BE │ path bytes   │ 8B finger  │ 32B token  │ 8B ts BE   │
  └────────────────┴──────────────┴────────────┴────────────┴────────────┘
  ```

  There is **no magic number** at the start, **no version
  byte**, and **no HMAC**. The `DPAPI unprotect` in
  `decrypt` ensures the blob was encrypted with the
  current Windows user's master key — but once decrypted,
  `deserialize` will accept **any well-formed** payload
  that another process (running as the same user) can
  produce. This includes a payload generated by a
  different instance of the same user (a second BitNet
  session, a different product that uses the same DPAPI
  protection shape, a malicious in-process attack that
  can call `decrypt` on attacker-supplied bytes).
- **PoC (Attack Scenario):**
  1. Attacker has any process running as the legitimate
     Windows user (e.g. a malicious browser extension that
     can spawn a child process).
  2. Attacker crafts a `SessionToken` blob with
     `vault_path = "<any vault path>"`,
     `vault_fingerprint = <any 8 bytes>`,
     `token = <attacker's 32-byte HMAC key>`,
     `created_at = <any u64>`. Uses
     `Windows.Security.Cryptography.DataProtection` to
     protect it for the current user.
  3. Attacker writes the result to
     `%APPDATA%\BitNet\session.bin`.
  4. When the user starts BitNet, the daemon / CLI's
     `SessionToken::decrypt` is called → DPAPI unprotect
     succeeds → `deserialize` accepts the crafted
     payload → the daemon is "unlocked" with the
     attacker's HMAC key.
  5. Attacker authenticates to the daemon over IPC with
     requests signed under their key.
- **Impact:** Authentication bypass. The attacker can
  read / modify / add / delete vault entries **without
  ever knowing the master password**. The WindowsHello /
  biometric unlock path also short-circuits because the
  session is already "valid".
- **Mitigations already in place:** DPAPI is per-Windows-
  user, so a different user (even admin) cannot craft a
  blob. But that is **coarse-grained** — every process
  running as the same user can craft one.
- **Fix:** Add a magic number (`b"BNST\x01\x00\x00\x00"`)
  and a 16-byte HMAC-SHA-256 over the serialized fields
  using a **per-vault** key derived from the vault's
  Argon2id hash. The HMAC prevents an attacker who can
  call `DPAPI unprotect` from substituting an alternate
  token without knowing the vault password. The magic /
  version lets us reject old-format blobs without
  ambiguous behavior.

  Patched `serialize`:
  ```rust
  fn serialize(&self) -> Vec<u8> {
      let path_bytes = self.vault_path.as_bytes();
      let mut out = Vec::with_capacity(
          MAGIC.len() + 4 + path_bytes.len() + 8 + 32 + 8 + 32,
      );
      out.extend_from_slice(MAGIC);
      out.extend_from_slice(&self.version.to_be_bytes());
      out.extend_from_slice(&(path_bytes.len() as u32).to_be_bytes());
      out.extend_from_slice(path_bytes);
      out.extend_from_slice(&self.vault_fingerprint);
      out.extend_from_slice(&self.token);
      out.extend_from_slice(&self.created_at.to_be_bytes());
      out.extend_from_slice(&self.hmac);  // [BITNET-H6] added
      out
  }
  ```

  Patched `deserialize`:
  ```rust
  fn deserialize(data: &[u8]) -> Result<Self, CoreError> {
      if data.len() < MAGIC.len() + 4 + 8 + 32 + 8 + 32 {
          return Err(CoreError::SessionLocked);
      }
      if &data[..MAGIC.len()] != MAGIC {
          return Err(CoreError::SessionLocked);
      }
      let version = u32::from_be_bytes(
          data[MAGIC.len()..MAGIC.len() + 4].try_into().unwrap());
      if version != SUPPORTED_VERSION {
          return Err(CoreError::SessionLocked);
      }
      // ... existing length-prefix + path + fields ...
      // Verify HMAC
      let hmac = <[u8; 32]>::try_from(&data[data.len() - 32..])
          .map_err(|_| CoreError::SessionLocked)?;
      if !constant_time_eq(&expected_hmac, &hmac) {
          return Err(CoreError::SessionLocked);
      }
      Ok(Self { /* ... */ })
  }
  ```

### 3.2 MEDIUM (4)

#### [BITNET-M10] `SaveVault_Click` keeps master password in managed string before SecureString wrap
- **CWE:** CWE-316
- **File:** `BitNet.Desktop/Views/VaultPage.xaml.cs:313`
- **Component:** C#
- **Description:** `var password = pwdBox.Password ?? "";`
  creates a managed `String` snapshot of the
  `PasswordBox.Password` property. The string lives in
  the managed heap until the GC reclaims the
  `SaveVault_Click` method's stack frame. The string is
  then converted to a `SecureString` (line 329-331), but
  the original `String` is **not zeroized** (managed
  strings are immutable; you cannot mutate them in
  place). The `password = string.Empty` reassignment
  on line 243 in the same file's `CopyPassword_Click`
  is correctly a no-op (the original allocation is
  unaffected) but the comment claims it provides
  mitigation — it does not.
- **Impact:** Local heap-inspection attack (debugger,
  pagefile) can read the master password.
- **Fix:** Read the password directly into a `SecureString`
  via `PasswordBox.SecurePassword` (which already returns
  a `SecureString`), or pin the `String` and zero the
  pinned buffer. Sample patched handler:
  ```csharp
  var secPwd = pwdBox.SecurePassword; // SecureString already
  // Pass directly to FFI:
  var saveResult = BitnetCore.SecureVaultSaveSecure(
      App.VaultPath, secPwd);
  secPwd.Dispose();
  ```

#### [BITNET-M11] `SettingsPage.ThemeRadioButtons_SelectionChanged` overwrites persisted preference on page load
- **CWE:** CWE-841 (Improper Enforcement of Behavioral
  Workflow)
- **File:** `BitNet.Desktop/Views/SettingsPage.xaml.cs:124-138`
- **Component:** C#
- **Description:** When the Settings page is first loaded,
  `OnLoaded` sets `ThemeRadioButtons.SelectedIndex = (int)theme`
  (line 53) to reflect the saved preference. This
  assignment **fires** the `SelectionChanged` event, which
  in turn calls `AppThemeService.Save(pref)` (line 129).
  The call re-saves the **same** value that was just
  loaded — but if the `SelectedIndex` assignment happens
  before the `SelectionChanged` handler is wired (race
  during `InitializeComponent`), or if the user later
  changes the selection and the order of events is
  non-deterministic, the preference can be clobbered. The
  bigger risk is **race during process startup**: if the
  RadioButtons render the `Index=0` placeholder (Default)
  before `SelectedIndex = (int)theme` is set, the
  `SelectionChanged` fires once with `pref=SystemDefault`
  and **overwrites** the user's saved `Light` / `Dark`
  preference on the very first launch after the WIP
  helper merge.
- **PoC:** 1) Open Settings, change to "Dark". 2) Close
  the app. 3) Reopen, navigate to Settings (the page
  loads; `OnLoaded` sets SelectedIndex; depending on
  WinUI event ordering, the SelectionChanged may fire
  with the value as it transitions from 0 → 1 → 2). 4)
  If the race fires with 0 (SystemDefault), the persisted
  preference is silently reset.
- **Fix:** In `OnLoaded`, wrap the `SelectedIndex` setter
  in a `_isInitialising` guard that suppresses the
  `Save` call. The pattern:
  ```csharp
  private bool _isLoadingPreference;

  private void OnLoaded(...) {
      _isLoadingPreference = true;
      try {
          ThemeRadioButtons.SelectedIndex = (int)theme;
      } finally {
          _isLoadingPreference = false;
      }
  }

  private void ThemeRadioButtons_SelectionChanged(...) {
      if (_isLoadingPreference) return;
      // ... Save ...
  }
  ```

#### [BITNET-M12] `MainWindow.Closed` removes WindowsHello credential even on FFI failure
- **CWE:** CWE-754 (Improper Check for Unusual or
  Exceptional Conditions) / CWE-841
- **File:** `BitNet.Desktop/App.xaml.cs:41-56`
- **Component:** C#
- **Description:** The `MainWindow.Closed` handler calls
  `BitnetCore.bitnet_vault_lock()` inside an unprotected
  block, then unconditionally calls
  `WindowsHelloHelper.RemoveCredential(VaultPath)`. If
  the FFI call panics (FFI state poisoned, native DLL
  unloaded, etc.), `WindowsHelloHelper.RemoveCredential`
  is **still** called because the handler is not wrapped
  in try/catch around the lock call. The user is left
  in a state where the vault is *not* locked (the lock
  call panicked mid-execution) but the WindowsHello
  credential is gone, so the next launch forces a master-
  password re-entry even though the vault is technically
  in an unlocked state.
- **PoC:** During a vault operation, an attacker DLL
  (or a bug in the FFI) raises a SEH exception that
  Rust's panic handler translates into a process abort
  *between* the `bitnet_vault_lock` call and the
  `WindowsHelloHelper.RemoveCredential` call. The user
  sees the app crash, restarts, and the WindowsHello
  prompt is gone — but the in-process daemon (if any)
  still holds the session token.
- **Fix:** Wrap each side-effectful call in its own
  try/catch, and only proceed to the next if the prior
  step succeeded:
  ```csharp
  MainWindow.Closed += (s, e) => {
      try { BitnetCore.bitnet_vault_lock(); }
      catch (Exception ex) {
          Debug.WriteLine($"vault_lock failed on close: {ex.Message}");
      }
      DaemonLauncher.Instance.Dispose();
      if (!string.IsNullOrEmpty(VaultPath)) {
          try { WindowsHelloHelper.RemoveCredential(VaultPath); }
          catch (Exception ex) {
              Debug.WriteLine($"RemoveCredential failed: {ex.Message}");
          }
      }
  };
  ```

#### [BITNET-M13] `EntryTypeIcons.Label` returns "Other" for unknown kind, while `ParseKind` defaults to "Login"
- **CWE:** CWE-754 / CWE-1284
- **File:** `BitNet.Desktop/Helpers/EntryKind.cs:65` and
  `BitNet.Desktop/Helpers/EntryTypeIcons.cs:65`
- **Component:** C#
- **Description:** `EntryKindExtensions.ParseKind("xyz")`
  returns `EntryKind.Login` (the default for unknown
  values), but `EntryTypeIcons.Label(EntryKind.Login)`
  returns "Login", not "Other". When the Rust core emits
  a kind that is not in the switch (e.g. "api_key" for a
  v0.2 entry), the UI shows "Login" instead of a
  distinctive "Unknown / Other" label. This is a small
  information disclosure / classification problem: a
  user looking at the vault list sees "Login" for a
  category that does not exist in the v0.1 enum, and
  cannot tell that the entry is in an unrecognised
  category.
- **Impact:** Minor classification bug; not a security
  vulnerability per se but the asymmetry between
  `ParseKind` (default-to-Login) and `Label` (default-
  to-Other) means a single round-trip through both
  functions loses information.
- **Fix:** Make `ParseKind` return a
  `Result<EntryKind, ()>` (or add a `bool isUnknown` out
  parameter) and have the icon-mapping site display
  "Other" for the unknown case.

### 3.3 LOW (2)

#### [BITNET-L2] `AppThemeService.Save` writes LocalSettings synchronously on UI thread
- **CWE:** CWE-459 (Incomplete Cleanup) — not a real
  security issue, but a UX / responsiveness issue.
- **File:** `BitNet.Desktop/Helpers/AppThemeService.cs:58-72`
- **Component:** C#
- **Description:** `LocalSettings.Values[Key] = (int)preference`
  is a synchronous disk write. It is called from the UI
  thread on every `SelectionChanged` event. On slow
  storage (e.g. an over-quota OneDrive sync) this can
  freeze the UI for tens of milliseconds.
- **Fix:** Debounce the `Save` call (e.g. with a 500 ms
  `DispatcherQueueTimer` reset on each `SelectionChanged`)
  so rapid clicks coalesce into a single write.

#### [BITNET-L3] `MainWindow` navigation order leaves `AutoLockService` permanently `_isLocked = true` until first unlock
- **CWE:** not a security issue per se; documentation
  hazard.
- **File:** `BitNet.Desktop/MainWindow.xaml.cs:19, 102`
- **Component:** C#
- **Description:** The `MainWindow` constructor navigates
  to `UnlockPage` *before* `AutoLockService.Instance.Load()`
  is called. The navigation fires `ContentFrame_Navigated`,
  which calls `AutoLockService.Instance.LockNow()`
  (because the page is `UnlockPage`). Then `Load()` runs
  and reads the timeout setting from `LocalSettings`, but
  it does **not** clear `_isLocked`. This means
  `AutoLockService._isLocked` starts as `true` and stays
  `true` until the user unlocks the vault (which
  navigates to a non-Unlock page and fires
  `AutoLockService.Instance.Reset()`).
  The auto-lock timer is therefore suppressed during the
  initial unlock screen. This is *probably* the intended
  behaviour, but it is **fragile** — if a future
  refactor moves the `Load()` call before the
  `Navigate()`, the `LockNow()` will fire *after* the
  `Reset()`-able state is set up, and the vault will
  auto-lock the moment the user looks at the unlock
  page.
- **Fix:** In the constructor, reorder so that
  `AutoLockService.Instance.Load()` runs *before*
  `ContentFrame.Navigate(typeof(Views.UnlockPage))`, or
  call `AutoLockService.Instance.Reset()` after the
  Load to make the unlocked-state the explicit
  initial state.

### 3.4 INFO (1)

#### [BITNET-I2] `MainWindow.Closed` swallows all exceptions silently
- **CWE:** CWE-396 (Declaration of Catch for Generic
  Exception)
- **File:** `BitNet.Desktop/App.xaml.cs:34-38`
- **Component:** C#
- **Description:** `try { DaemonLauncher.Instance.EnsureRunning(); }
  catch { }` swallows every exception from
  `EnsureRunning`. This is intentional ("the GUI works
  without the daemon"), but with **no logging at all** the
  failure mode is invisible — a missing DLL, a missing
  VC runtime, a permission issue, all become "the GUI
  silently doesn't get IPC". The user has no idea why
  their browser extension can't talk to the desktop.
- **Fix:** Log to `Debug.WriteLine` or `tracing::error!`
  with the exception type and message. The log is free,
  the cost is one line of code, the diagnostic value is
  significant.

## 6. What's Done Well (post-WIP)

- The WIP refactor cleanly separates WinUI-coupled
  concerns (`EntryTypeIcons`, `AutoLockService`) from
  pure data (`EntryKind`, `AutoLockTimeout`,
  `AppThemePreference`), enabling unit tests on the data
  side without dragging in Microsoft.UI.
- `FavoriteJsonConverter` is defensive — accepts `true`
  / `false` / `1` / `0` / `"true"` / `"false"` and
  defaults to `false` on unparseable input rather than
  throwing, so a single malformed entry cannot lock the
  user out.
- The new `PasswordStrength.Score` is a textbook entropy
  approximation; it does **not** log the password, **not**
  compare it in non-constant time, and **not** leak it via
  telemetry.
- `DaemonLauncher.ResolveDaemonPath` is PATH-hijack
  resistant by design (resolves from
  `AppContext.BaseDirectory`, not from `PATH`).
- `MainWindow.OnUserActivity` fires `Touch()` on every
  pointer / key event with `handledEventsToo: true`, so
  child controls that mark events handled (e.g. a
  TextBox committing a keystroke) do not stop the
  activity tracking.
