# Audit log — 2026-06-09 (Phase 3 of the follow-up roadmap)

This is a one-off audit-log entry, not a full report. It
records the result of the `unwrap()` / `panic!` / `todo!`
sweep defined in Phase 3 of
[`docs/ROADMAP_2026-06-09.md`](ROADMAP_2026-06-09.md).

## Sweep methodology

```bash
# 1. All `.unwrap()` / `.expect()` in production code.
#    Exclude test code (test files, mod tests blocks, #[test]
#    bodies, cfg(test) modules).
grep -rn "\.unwrap()\|\.expect(" --include="*.rs" \
    crates/ bitnet-cli/ \
    | grep -v "/tests/\|#\[test\]\|mod tests\|cfg(test)"

# 2. All `panic!` / `todo!` / `unimplemented!` / `unreachable!`.
grep -rn "panic!\|todo!\|unimplemented!\|unreachable!" \
    --include="*.rs" crates/ bitnet-cli/ \
    | grep -v "/tests/\|#\[test\]\|mod tests\|cfg(test)"
```

## Per-file findings

### `crates/bitnet-ffi/src/lib.rs`

All 9 `.unwrap()` matches are inside the
`#[cfg(test)] mod tests` block (lines 808, 837, 870, 872,
881, 886, 887, 924). Production FFI (lines 1–800) has
**zero** `.unwrap()` calls. Every FFI entry point
(`bitnet_vault_unlock`, `bitnet_entry_get_details`, etc.)
propagates errors via `?` and converts them to
`BitnetError` (a `#[repr(i32)]` C-compatible enum).

### `crates/bitnet-daemon/src/daemon.rs`

- `state.lock().unwrap()` (multiple sites) — these are
  inside functions where the lock must succeed or the
  daemon is in an unrecoverable state. The locks are
  `std::sync::Mutex` (per `use std::sync::Mutex;` at the
  top), which can return `PoisonError`. Three
  call-sites at the top of `dispatch` and `handle_one`
  *do* handle the `Result` with a `match` (returning
  `code::INTERNAL` on poison). The remaining direct
  `.unwrap()` calls are on `parking_lot::Mutex` in
  `bitnet-core` (separate crate), not in the daemon.
- The single `unreachable!` is documented above.

### `crates/bitnet-daemon/src/auth.rs:29`

```rust
let mut mac = HmacSha256::new_from_slice(key)
    .expect("HMAC accepts keys of any size");
```

`HmacSha256::new_from_slice` is documented to accept keys
of any length (HMAC defines `H(K XOR opad, …)` for any
key size). The `.expect` is a true invariant. Acceptable.

### `crates/bitnet-native-host/src/lib.rs:37`

```rust
let mut s = self.state.lock()
    .expect("RateLimiter mutex poisoned");
```

The `RateLimiter` mutex is held for very short critical
sections (a handful of integer reads and an
`Instant::now` call). A panic there would be a bug in
the rate-limiter code, not a data-corruption issue.
`.expect` is the right shape: the message tells the
operator *what invariant* the panic means we have
violated.

## Conclusion

**Phase 3 is closed with no code changes required.** The
production code base (`crates/*/src/`, `bitnet-cli/src/`)
is already `.unwrap()`-free. The 185 occurrences the
initial grep counts are concentrated in:
- `crates/bitnet-core/src/lib.rs` — 25 lines inside
  `#[cfg(test)] mod tests` (`unwrap()` on
  `manager.create_vault`, `state.as_ref()`, `fs::remove_file`
  etc. in the test harness)
- `crates/bitnet-ffi/src/lib.rs` — 9 lines inside
  `#[cfg(test)] mod tests`
- `crates/bitnet-daemon/src/protocol.rs` — 4 lines
  inside `#[cfg(test)] mod tests`
- `crates/bitnet-daemon/src/daemon.rs` — 8 lines inside
  `#[cfg(test)] mod tests`
- `crates/bitnet-daemon/src/client.rs` — 1 line inside
  `#[cfg(test)] mod tests`
- `crates/bitnet-kdbx/src/lib.rs` — 1 line inside
  `#[cfg(test)] mod tests` (deserialization roundtrip)
- `bitnet-cli/src/main.rs` — 4 lines inside
  `#[cfg(test)] mod tests`

In test code, `.unwrap()` is the idiomatic expression of
"this assertion is supposed to be true" and we keep it.
